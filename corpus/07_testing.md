# Испытания и сравнение вариантов Контура

## Цели испытаний

Проверки подтверждают не только запуск интерфейса, но и сохранность смысловой цепочки от файла до ответа. Успешная установка пакетов не доказывает, что страницы PDF читаются, ссылки ведут к нужному разделу, а база и векторы переживают перезапуск. Для испытаний используют небольшой детерминированный набор для логических свойств и содержательный демонстрационный корпус для сценариев поиска. Отчёт различает автоматические проверки, ручные наблюдения и операции, которые не удалось выполнить из-за отсутствующей локальной модели.

Испытательная среда фиксирует версию Python, установленные зависимости, используемые ID моделей и дату сборки корпуса. Измерения времени зависят от оборудования, поэтому рядом с числом указывают условия и объём входных данных. Нельзя переносить оценку задержки со стенда на производственную машину без нового опыта. Основная цель — обнаружить недостоверную ссылку или несогласованный снимок до передачи сервиса читателям, а не добиться красивого среднего времени любой ценой.

## Проверка извлечения и объёма

Для Markdown создают файл с несколькими уровнями заголовков, списком и кириллицей; ожидают сохранения текста и читаемого пути раздела. Для обычного текста проверяют пустые строки и абзацы, для кода — имя функции рядом с её содержимым. PDF с текстовым слоем должен сохранять номера страниц. Сканированный PDF без распознаваемых символов должен давать явное предупреждение вместо ложного результата с нулём «успешно прочитанных» страниц. Один сбойный файл из пакета не отменяет отчёты по остальным.

Подсчёт текстового объёма задают явно: слова считаются как последовательности букв и цифр с допустимым внутрисловным дефисом, заголовки относятся к тексту, Markdown-разметка сама по себе словами не является. Оценку страниц получают делением числа слов на пятьсот. В демонстрационном корпусе несколько тематических файлов важнее одного огромного документа, поскольку позволяют проверять правильность имени источника. Контроль объёма не должен поощрять бессмысленное повторение абзацев: он лишь гарантирует достаточную широту материала для поиска.

## Свойства фиксированного разбиения

Тестовый текст содержит длинное слово у предполагаемой границы, короткий документ, несколько абзацев и два разных файла. Проверяют, что обычное слово не разрезано посередине при доступной рядом границе, фрагменты не пусты и не перескакивают в соседний файл. Размер по умолчанию около тысячи символов, перекрытие около ста пятидесяти, но настройку можно изменить для проверки граничных случаев. Восстановление исходного текста по фрагментам с учётом перекрытия помогает обнаружить потерянные строки и случайные пропуски.

Отдельно изучают последние фрагменты: остаток из одного предложения не стоит без причины дублировать как новый почти идентичный чанк. Порядковые номера отражают движение по файлу, а имя источника постоянно для всех его частей. Если извлечение уже очистило переносы строк, проверку сравнивают с нормализованным текстом, а не с исходными байтами. Иначе тест ложно обвинит разбиение в преобразовании, выполненном на предыдущей стадии.

## Свойства структурного разбиения

Тестовый Markdown включает вложенные заголовки, пустую родительскую секцию, два одинаково названных подраздела в разных главах и длинный абзац. Структурные чанки обязаны сохранить различимый путь заголовков и не объединять сведения из разных файлов. Длинную секцию делят на границах абзацев или предложений; короткие абзацы объединяют без потери порядка. Для PDF без оглавления разумной единицей может стать страница, а для текста без заголовков — абзац и имя файла.

Проверяют, что слишком длинный раздел действительно делится, а не остаётся непригодным для ограниченного контекста. Обратная проверка выявляет сотни микроскопических чанков там, где два соседних абзаца относятся к одной теме. Если раздел пересекает страницы PDF, номер страницы каждого фрагмента должен отражать происхождение текста, а не номер первой страницы всего документа. Такие свойства нельзя надёжно оценить только по общему числу чанков: требуется смотреть отдельные образцы и метаданные.

## Векторизация и поиск

Для детерминированного теста используют малый набор заранее заданных числовых векторов, не зависящий от работы LM Studio. Проверяют нормализацию, ожидаемый порядок ближайших соседей и правильную связь результатов FAISS с текстовыми строками SQLite через идентификатор вектора. Отдельные случаи охватывают нулевой вектор, неверную размерность и нечисловое значение. Такие входы не должны незаметно создавать валидный на вид индекс или ответ. Поиск на пустом наборе сообщает об отсутствии результатов, а не возвращает произвольный документ.

Испытание на реальной embedding-модели выполняют отдельно, когда локальный сервер доступен. Пробный вопрос выбирают по заранее известному документу. В отчёте записывают модель, корпус, стратегию, топ-k, оценки и найденные файлы. Даже если численное сходство высоко, открывают хотя бы несколько результатов и сверяют смысл. Порядок похожих фрагментов может изменяться при смене модели; это причина повторить проверку, но не автоматическое доказательство регрессии.

## Сохранение и перезапуск

Программа создаёт SQLite и оба файла FAISS, после чего процесс завершают и запускают заново. Новый процесс обязан загрузить активную версию и получить тот же идентификатор чанка для известного числового ID вектора. Открывают сохранённый диалог и проверяют порядок сообщений, режимы и источники. Тест повторной индексации убеждается, что активный набор не удвоился, если оператор построил тот же корпус ещё раз. Согласованность источника нельзя проверять только сравнением количества строк: разные документы могут дать одинаковое число чанков.

Сценарий ошибки прерывает сборку до публикации, например искусственным исключением при сохранении. Предыдущий комплект остаётся пригодным для чтения; половина нового индекса не становится активной. Если база и файлы индекса расходятся, загрузка должна явно отклонить несовместимую версию. Ручной опыт дополняет автоматический: после полного перезапуска браузера и Python-процесса пользователь открывает знакомый вопрос и видит прежние карточки без повторной загрузки исходников.

## Проверка запросов к chat-модели

На подменённом локальном API проверяют состав входного запроса без внешней сети. Для режима «С RAG» в сообщениях присутствуют вопрос, ограниченная история и найденный контекст с метками источников. Документальный текст обозначен данными, а правила ответа требуют признать отсутствие сведений и назвать источники. Для режима «Без RAG» ни найденных фрагментов, ни искусственных карточек источников нет. Проверяют, что ограничение длины истории не удаляет текущий вопрос и что число контекстных символов не растёт без границ.

Потоковая выдача ответа тестируется с последовательностью частей, включая пустую часть и завершение потока. Если сервер поток не поддерживает, интерфейс может показать итоговый ответ обычным способом, но не должен дополнять его выдуманной частью. Ошибки соединения и несовместимой модели оформляют коротким сообщением пользователю и подробной диагностикой в соответствующем канале. Проверка с подменённым API подтверждает код интеграции, но не означает, что реальные модели установлены и отвечают на конкретной машине.

## Контрольные вопросы и интерпретация Hit@5

Контрольный набор содержит не меньше десяти вопросов с заранее заданным файлом и, по возможности, названием раздела. Вопросы формулируют так, как спросил бы сотрудник, а не как дословную копию заголовка. После построения обоих индексов один и тот же вопрос ищут в каждой стратегии. Попадание ожидаемого файла в первые пять результатов считается успехом для Hit@5. Название раздела помогает человеку понять качество попадания, даже когда автоматическая оценка реализована только по имени файла.

В отчёте приводят оба значения и список промахов, а не одно число без контекста. Если вопрос касается утверждения из двух разных файлов, для учебного эталона выбирают наиболее прямой источник и описывают альтернативы отдельно. Не следует выдавать Hit@5 за оценку фактической точности ответа LLM: генерация может ошибиться и при наличии правильного чанка. Неудачный результат полезен для пересмотра заголовка, разбиения, модели или формулировки вопроса, но эталон не переписывают задним числом только ради повышения показателя.

## Ручной маршрут демонстрации

Оператор выбирает демонстрационный корпус одной кнопкой и смотрит статистику извлечения. Затем строит обе стратегии на доступной embedding-модели, открывает примеры чанков и проверяет имя файла и раздел. Во вкладке сравнения он задаёт контрольный вопрос о восстановлении из резервной копии и смотрит две колонки результатов. После этого создаёт диалог с RAG, задаёт вопрос о скане PDF и проверяет карточку источника. Следующее сообщение отправляет без RAG и убеждается, что подтверждённые ссылки не появились.

Завершив процесс приложения, оператор запускает его заново и открывает прежний диалог. Он проверяет сохранённые режимы и возможность нового поиска по загруженным индексам. Если LM Studio на машине не запущен, этот маршрут нельзя считать завершённым: автоматические тесты с подменой отмечают отдельно, а шаги с реальной моделью остаются непроверенными. Дисциплина отчёта не мешает пользоваться кодом, но защищает следующего пользователя от неверного впечатления о фактически проведённых испытаниях.

## Решение о готовности

Релизный протокол перечисляет набор документов, число слов и оценочных страниц, размеры индексов, ID моделей, число чанков и фактические результаты контрольного поиска. Отдельно отмечают, какие проверки были выполнены автоматически, какие вручную, а какие заблокированы отсутствием сервера или нужной модели. Неудачный тест нельзя превращать в «известное ограничение» без оценки влияния: потерянная страница PDF и неверная связь вектора с текстом имеют разный риск, но оба могут менять ответ.

Решение о передаче учебного стенда принимает ответственный после просмотра не только зелёных индикаторов, но и карточек результатов. Для рабочего внедрения потребуются дополнительные меры: разграничение доступа, согласованный регламент хранения и проверка локальной инфраструктуры. Демонстрационный корпус нужен для объяснения принципов и тренировки диагностики; он не даёт полномочий применять вымышленные правила к настоящему оборудованию.
