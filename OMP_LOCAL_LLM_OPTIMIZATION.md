# Задание для Oh My Python (OMP): приложение для оптимизации локальной LLM

Реализуй в текущем проекте работающее локальное веб-приложение на Python для общения с моделями LM Studio и сравнения настроек модели **до и после оптимизации**. Выполни работу до запускаемого результата: исходный код, интерфейс, база данных, проверки и инструкция. Не останавливайся на плане или прототипе экрана.

Если в проекте уже есть чат с LM Studio, сначала изучи его и расширь существующую реализацию. Сохрани работающие функции и данные; не создавай второй независимый чат без необходимости. Если проект пуст, создай приложение с нуля.

## Что должно получиться

1. Обычный чат с выбранной локальной моделью, потоковым ответом и историей после перезапуска приложения.
2. Редактор профилей: модель, температура, предел выходных токенов, контекстное окно, system prompt.
3. Выбор установленного варианта квантования модели, если в LM Studio есть несколько вариантов.
4. Экран сравнения двух профилей на одинаковых тестовых вопросах с сохранением ответов, ручной оценкой качества, скоростью и метриками ресурсов.
5. Выгружаемый отчёт, по которому можно обосновать результат учебного задания «Оптимизация локальной LLM».

Приложение должно работать без облачных моделей. Не добавляй обращений к внешним API, CDN или облачным сервисам во время его работы.

## Технологии и границы

- Python 3.11+, FastAPI, SQLite, HTML/CSS/JavaScript без обязательной сборки фронтенда.
- Один пользователь, запуск на `127.0.0.1`; авторизация не нужна.
- Адрес LM Studio задаётся переменной окружения, по умолчанию `http://127.0.0.1:1234`. Веб-страница не должна принимать произвольный адрес сервера.
- Целевая версия LM Studio — 0.4.0 или новее. Если необходимая возможность API отсутствует, выведи понятное сообщение.
- В первую версию входят только текстовые диалоги и текстовые тестовые вопросы. RAG, обучение весов и автоматическая загрузка моделей из интернета не нужны.

## Интеграция с LM Studio

Используй локальный API LM Studio:

| Функция | Endpoint |
| --- | --- |
| Список локальных моделей, квантований и вариантов | `GET /api/v1/models` |
| Загрузка модели с нужным контекстным окном | `POST /api/v1/models/load` |
| Потоковая генерация с полной историей сообщений | `POST /v1/chat/completions` |

Для чата передавай `model`, массив `messages`, `temperature`, `max_tokens`, `stream: true` и `stream_options: {"include_usage": true}`. System prompt профиля добавляй первым сообщением. Историю загружай из собственной SQLite-базы и отправляй с каждым запросом, чтобы продолжение чата не зависело от внутреннего состояния LM Studio.

Контекстное окно — настройка загрузки модели. При его изменении явно загружай или перезагружай модель с новым `context_length`, сверяй результат с фактической конфигурацией и показывай время загрузки отдельно от времени генерации. Не меняй параметры уже выполняющегося запроса. Запуски сравнения выполняй последовательно.

**Квантование весов нельзя менять ползунком для уже скачанного файла.** Показывай метаданные установленного варианта (`Q4`, `Q8` и т. п., размер файла) и разрешай выбрать другой вариант только если он реально доступен в LM Studio. Для сравнения квантования использовать варианты одной базовой модели. Если нужный вариант не установлен, объясни, что его следует предварительно скачать в LM Studio.

## Интерфейс

Сделай три понятных раздела:

### Чат

- Создание, открытие, переименование и удаление чатов.
- Выбор сохранённого профиля перед отправкой сообщения.
- Потоковое отображение ответа.
- Под каждым ответом: фактически использованная модель/квантование, настройки, полное время ответа, время до первого фрагмента, входные и выходные токены, статус.
- Сохранение истории между перезапусками. При ошибке LM Studio сохранённые чаты остаются доступными.

### Профили

- Создание, копирование и редактирование профилей.
- Поля: название, установленная модель/вариант, `temperature`, `max_tokens`, `context_length`, system prompt.
- Показывай поддерживаемый моделью предел контекста и проверяй ввод до сохранения.
- Добавь два примерных профиля для кейса «помощник по Python»: базовый и оптимизированный. Примерные параметры можно менять; не утверждай заранее, что оптимизированный профиль объективно лучше.

### Сравнение

- Пользователь создаёт набор тестовых вопросов и при желании записывает эталонные факты или критерии ответа.
- Выбирает базовый и оптимизированный профили, число повторов (по умолчанию 3) и запускает опыт.
- Каждый профиль получает одинаковые вопросы в отдельной чистой сессии; ответы одного профиля не попадают в контекст другого.
- Отображай ответы рядом, сырые метрики и итоговую таблицу различий.
- Дай вручную оценить точность, полноту и соблюдение формата по шкале 1–5. Показывай средние оценки и количество оценённых ответов; не используй другую LLM как автоматического судью.
- Позволь выгрузить отчёт в Markdown или CSV с вопросами, ответами, снимками настроек и методикой измерения.

## Метрики и методика

- Измеряй полное время ответа монотонными часами Python от начала запроса к LM Studio до завершения потока. Отдельно измеряй время до первого текстового фрагмента.
- Входные и выходные токены бери из `usage` ответа LM Studio. Если данных нет, записывай `NULL` и показывай «н/д»; не подменяй токены числом слов.
- Скорость токенов/с считай только если есть выходные токены и длительность генерации. Укажи формулу в отчёте.
- Перед измеряемыми повторами сделай один прогревочный запрос и не включай его в агрегат. Время холодной загрузки модели показывай отдельно. Для итоговых времён и скорости выводи медиану повторов.
- Для оценки RAM попробуй измерять RSS процессов LM Studio и его движка через `psutil`, с явным указанием измеренных PID/имён процессов и источника данных. Записывай значение после загрузки и пик во время генерации. Если невозможно надёжно определить нужный процесс, показывай «н/д» с причиной. Не называй общий расход памяти компьютера расходом конкретной модели. GPU/VRAM — только при наличии надёжного локального источника.
- Сохраняй размер файла модели из метаданных LM Studio как отдельный показатель ресурсов.
- При превышении контекста показывай ошибку. В сравнительном тесте не обрезай текст или историю молча.

## Хранение данных

Используй SQLite как основной источник данных. Нужны сущности:

- `profiles` — редактируемые профили;
- `chats` и `messages` — история и метрики каждого ответа;
- `test_suites` и `test_cases` — наборы одинаковых вопросов;
- `experiment_runs` и `experiment_results` — запуски, ответы, повторы, ручные оценки и измерения.

Для каждого ответа и запуска сохраняй **неизменяемый снимок настроек**: модель, вариант квантования, фактическое окно контекста, температуру, максимум токенов и system prompt. Редактирование профиля позднее не должно переписывать старые результаты. Предусмотри безопасную инициализацию или миграцию схемы без потери истории.

## Надёжность

- Проверяй диапазоны параметров, длину сообщения, существование модели и доступность LM Studio.
- Не сохраняй частичный ответ как успешно завершённый. Для ошибки и обрыва потока храни отдельный статус.
- Безопасно выводи текст пользователя и модели: не вставляй его в DOM как необработанный HTML.
- Показывай понятные ошибки для выключенного LM Studio, незагруженной модели, неверного контекстного окна и нехватки памяти при загрузке.
- Храни адрес LM Studio и путь к базе в `.env.example`; не фиксируй их в коде как единственно допустимые значения.

## Порядок работы

1. Изучи текущий проект и найди существующие функции чата и хранения, если они есть.
2. Реализуй слой SQLite и клиент LM Studio; затем чат и профили.
3. Реализуй последовательный запуск сравнений, сбор метрик, ручные оценки и экспорт отчёта.
4. Проверь автоматическими тестами работу с подменёнными ответами LM Studio: сохранение истории, снимки настроек, поток, отсутствие `usage`, ошибки, смену контекста и запуск сравнения.
5. Если локальный LM Studio доступен, проведи короткую проверку с реальной моделью. Если нет, не блокируй завершение: опиши точные шаги ручной проверки в README.
6. Создай `README.md` с установкой, запуском LM Studio, запуском веб-приложения, настройками окружения и методикой сравнения.

## Условия готовности

Работа завершена, когда пользователь может открыть приложение локально, создать и продолжить чат, выбрать модель и настройки, провести сравнение двух профилей на одинаковых вопросах, сохранить ручные оценки и скачать отчёт. История и результаты должны переживать перезапуск веб-приложения. Квантование должно отражать реально выбранный вариант модели; контекстное окно — реально применённую конфигурацию загрузки.

В финальном сообщении перечисли созданные файлы, команды запуска, результаты проверок и ограничения измерения RAM/GPU. Не называй приложение проверенным на реальной модели, если проверка была только с подменённым сервером.
